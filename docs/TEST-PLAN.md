# Test plan - pointer, battery, scroll, enable/disable

Hardware on a Windows 10/11 PC with Magic Tray running. Record tray version (footer), Windows build, and `diagnose-and-recover.ps1` output after any failure.

Catalog PIDs: v1 `030D`, v3 `0323`. Skip rows for a mouse that is not present.

## A. Magic Mouse v3 (USB-C, `0323`)

Setup: paired over Bluetooth, USB-C unplugged, Test Mode on, Memory integrity off, KMDF bound.

| # | Action | Pointer | Battery | Scroll |
|---|---|---|---|---|
| A1 | Move / click | Cursor moves | - | - |
| A2 | Tray **Refresh Now** | - | Percent, Input 0x90 COL02 | - |
| A3 | Two-finger swipe | - | - | Content scrolls |
| A4 | Plug USB-C, charge 1 min or more | May switch to USB HID (no wheel) | Percent may jump (0 to 100) | Wheel may die on USB. Expected. |
| A5 | Unplug, wait 10 s | Bluetooth pointer | Percent again | **Wheel must return** |
| A6 | If A5 wheel dead | Tray problem row -> auto-fix (see D), or `diagnose-and-recover.ps1 -Repair` | Unchanged | Wheel returns; the service named in the device's `LowerFilters` (on this PC `MagicMouseDriver204Scroll`) is STATE=RUNNING |
| A7 | Tray **Windows device -> Stop this device in Windows**, then **Start this device in Windows** (do **not** Remove in Settings) | Stops, then starts | Follows | Follows |
| A8 | Tray **Show in Magic Tray** off, then on | Keeps working - pure config, no PnP change, no UAC | Poller skips the PID while it is off; a row still drawn reads `Off in this app` | Keeps working |

Pass A5 or A6. Fail only if the wheel is dead while the **bound** filter service reports RUNNING, or if the tray badges KMDF while the **bound** service is STOPPED. The first of those shapes now has **two** diagnoses, and one read of `DEVPKEY_Device_Stack` on the live BTHENUM instance separates them: the bound filter **absent** from the stack is fault A, registered and loaded but **not attached** to this mouse's stack, which is D18 to D21 below; the bound filter **present** in the stack with the wheel still dead is fault B, the mouse never received the Apple multi-touch enable feature report `{0xF1, 0x02, 0x01}` on COL01, which is D22 to D24 below and is owned by the driver package's F1 watcher, not by the tray (see "Which dead-wheel fault is this" in `docs/ENABLE-DISABLE.md`). Do not judge by `sc query MagicMouseDriver`: on this PC that older service is installed but not bound, and it is Stopped even when scrolling works. `sc start` on a lower filter always exits 31 and means nothing.

## C. App - enable/disable and Diagnostics

| # | Action | Expected |
|---|---|---|

## D. In-app repair (problem row, guided dialog, auto-fix)

The zero-PowerShell path. Reproduce each state on hardware, then work the row the tray offers.

| # | Check |
|---|---|

| D1b | **False-positive regression.** On the reference PC the 0323 device binds `MagicMouseDriver204Scroll` (RUNNING) while an older, unbound `MagicMouseDriver` service is installed and Stopped. Confirm the tray still reports **No driver or connection problems found**: `sc query MagicMouseDriver204Scroll` RUNNING, `sc query MagicMouseDriver` STOPPED, wheel scrolls. A stopped same-family service that is not in the device's `LowerFilters` must produce no finding and no toast. |

| D3 | Open that row: the guided dialog states the PID, what was found, the cause, and what the fix will do **before** anything runs. No device is touched until you press the action button. |
| D4 | Press the fix (one UAC prompt): the app runs `pnputil /restart-device` on the live **BTHENUM** instances only - no `sc start` in `debug.log` - the bound filter service comes back to STATE=RUNNING because PnP reloaded it with the stack, and the **wheel scrolls again**. | D5 | Verify the fix left the rest alone: still paired, USB / `HID\VID_` phantoms untouched, Bluetooth radio on, no `FLIP:NoFilter` in `debug.log`. |

| D8 | USB charge-cable phantoms only (no live BTHENUM) on a PID this PC has an `enabled_<pid>` entry for: the row says the mouse is not connected over Bluetooth and that the phantoms must be left alone. Nothing is enabled or restarted. |

After it runs `config.ini` reads `enabled_<pid>=true` with the device working. No `pnputil` runs for this one: the tray state is pure config. |
| D10 | Toast behaviour: a detected problem toasts **once per problem per session**. Re-open the menu, refresh, or leave it running - no repeat toast for the same problem. Restart the tray with the problem still present: one toast again. |
| D11 | **Ownership regression (22 findings).** On a PC that owns two Apple devices, the tray must report at most those two and never the rest of the catalog: with both healthy the menu reads **No driver or connection problems found**, and with one fault exactly one row appears. Confirm in `debug.log` that a menu open writes a `REPAIR_SNAPSHOT` line only for PIDs with live BTHENUM nodes, USB phantoms, or an `enabled_<pid>` entry - not one line per catalog PID. A catalog keyboard or trackpad this PC has never had produces no snapshot line and no finding. The bug this pins reported `REPAIR_FINDINGS count=22` on a two-device PC. |
| D12 | **Two scroll drivers registered.** On the reference PC state (device key `LowerFilters=[MagicMouseDriver]` with that service Stopped, instance key `LowerFilters=[MagicMouseDriver204Scroll]` with that service Running, both under `HKLM\SYSTEM\CurrentControlSet\Enum\BTHENUM`): the tray reports one problem row for `0323` naming the conflict while the working filter is RUNNING. `debug.log` shows the `REPAIR_SNAPSHOT` line listing both candidates. |
| D13 | Open that row: the dialog names **both** drivers before anything runs - the leftover it will remove (`MagicMouseDriver`) and the working one it keeps (`MagicMouseDriver204Scroll`) - plus one admin prompt, no unpairing. Cancel touches nothing: re-read the registry and both `LowerFilters` values are unchanged. |
| D14 | Press the fix (one UAC prompt): afterwards exactly **one** family filter name is registered across the device key and the instance key (`MagicMouseDriver204Scroll` only), the leftover is gone, and the **wheel scrolls again**. `debug.log` records the previous `LowerFilters` value verbatim before the write. |
| D15 | After D14 the battery percent returns on a later poll (**Refresh Now** once or twice): the COL02 vendor report stops coming back zeroed `[90 00 00]` and a percent appears again. Pointer and clicks work throughout. |
| D16 | Correctly installed PC (one vendor filter name on the stack, service RUNNING): **No conflict reported.** The menu reads **No driver or connection problems found**, no toast, no dialog - a single-filter stack must never be diagnosed as a conflict. |
| D17 | **Refusal check.** With only one family filter registered (or with the leftover already removed), the repair must refuse to remove the last remaining filter: no `LowerFilters` value is emptied, no service key or `.sys` is deleted, non-family filters (`mouhid`, `HidBth`) stay in place, no `FLIP:NoFilter`, the radio is untouched, and USB / `HID\VID_` phantoms are not modified. Running the row in that state reports that nothing needed fixing. |
| D18 | **Wheel dead after a restart while the driver reads correct.** v3 `0323` with live BTHENUM instances, a bound filter name, the filter package present, `sc query <bound filter>` STATE=RUNNING, and that filter **absent** from `DEVPKEY_Device_Stack` (restart Windows and let PnP rebuild the stack from its cached HID layout; confirm the state with `Get-PnpDeviceProperty -InstanceId <bthenum instance> -KeyName DEVPKEY_Device_Stack`): the tray reports one row for `0323` titled **Scroll wheel is dead - the driver is not attached to this mouse** and offers the automatic restart. `debug.log` shows the stack read for that PID - `REPAIR_STACK pid=0323 bound=MagicMouseDriver204Scroll in_stack=false instances=1 readable=1` - and after the fix the `pnputil /restart-device` on the live **BTHENUM** instances only: no `sc start`, no `LowerFilters` write. |
| D19 | **Unknown is never a fault.** The same shape but with the property unreadable (no BTHENUM instance id resolves, or every property read fails): `debug.log` reads `in_stack=unknown` on the `REPAIR_STACK` line, or a `REPAIR_STACK_FAILED pid=0323 bound=... err=...` line, and the menu still reads **No driver or connection problems found**. No toast, no dialog, and nothing is restarted - confirm no repair ran. Unknown must not be treated as "not attached". |
| D20 | **Honest verification after the restart.** For this fault `sc query` was already RUNNING before the repair, so the service state proves nothing: after pressing the fix in D18 the tray re-reads `DEVPKEY_Device_Stack` and logs a second `REPAIR_STACK` line for the PID. Filter now in the stack (`in_stack=true`): success is reported and the **wheel scrolls again**. Filter still absent (`in_stack=false`): the tray must **not** claim success - it says Windows kept the cached layout for this mouse and shows the re-pair steps (Bluetooth & devices -> Remove device, power the mouse off and on, Add device). |
| D21 | **Healthy-mouse regression for the new rule.** A working mouse whose bound filter **is** in `DEVPKEY_Device_Stack` (wheel scrolls): **No driver or connection problems found**, no toast, no restart. An attached filter must never raise the new finding, whatever `LowerFilters` and the service state look like - this rule must not nag a working PC. |
| D22 | **Differential: filter attached and the wheel still dead is NOT a tray fault.** v3 `0323` with live BTHENUM instances, the bound filter name present, the package present, `sc query <bound filter>` STATE=RUNNING, and that filter **present** in `DEVPKEY_Device_Stack` (reference PC reads `\Driver\HidBth \| \Driver\MagicMouseDriver204Scroll \| \Driver\BthEnum`), `DEVPKEY_Device_ProblemCode` 0, both HID children OK - while the wheel does not scroll: the tray must report **NO problem for `0323`** (menu reads **No driver or connection problems found**, no toast, no dialog, nothing restarted; `debug.log` logs `in_stack=true`). **That is a PASS.** A tray finding in this state would be a **false positive** - every read is byte-identical to the same PC after scroll was restored (measured 2026-09-15). Redirect the tester to the driver repo's F1 watcher (`v2-kmdf-driver/scripts/mm-auto-f1-watcher.ps1` in `LesleyMurfin/magic-mouse-v3-windows-fix`): the mouse never got `{0xF1, 0x02, 0x01}` on COL01. |
| D23 | **A zeroed `0x90` pull is never a fault.** With a usermode `GET_REPORT(Input, 0x90)` pull on COL02 returning `[90 00 00]` on every poll, the tray must raise **nothing** from it: no problem row, no toast, no repair, and `MOUSE_BATTERY_ZERO` in `debug.log` keeps its "no battery report sent yet - idle mouse" reading. Cite the measurement: the same `[90 00 00]` came back 10/10 over 5 s on a **dead** wheel and 10/10 again on the **same PC with multitouch confirmed flowing**, so those zeros cannot discriminate a fault. The percent arrives as a **pushed** input report instead (healthy series 72/71/61/54/47/42 percent in `debug.log` up to 2026-09-15 01:58:49). |
| D24 | **Cross-repo expectation, owned by the driver repo.** On a PC using the KMDF `0323` driver, reboot Windows and touch nothing: multitouch must be live with **no manual step** (the F1 watcher's startup reconciliation, since at boot the mouse is already enumerated before an arrival-only subscription can see it). Verify by the **wheel scrolling** and the **battery percent reappearing on the next poll** (**Refresh Now** once or twice). A failure here is a driver-package bug, not a tray bug, and it must still leave the tray at **No driver or connection problems found** per D22. Listed here only so the tray tester knows the expected post-reboot state; Magic Tray does not send F1 and adding that is a non-goal. |
| D25 | **Pointer child gone while the Bluetooth parent is live.** v3 `0323` with live BTHENUM instances and the PID's Bluetooth-transport COL01 HID child registered under `HKLM\SYSTEM\CurrentControlSet\Enum\HID` but not resolving as present (disable just the COL01 HID child in Device Manager; confirm `CM_Locate_DevNodeW` cannot resolve it, e.g. `Get-PnpDevice -InstanceId <bluetooth col01 child>` reporting it not present): the tray reports **exactly one** row for `0323` naming the pointer child, and offers the automatic fix. `debug.log` shows the pointer probe result for the PID and, after the fix, the `pnputil /restart-device` on the live **BTHENUM** instances only - no `sc start`, no `pnputil` against a `USB\` or `HID\VID_` node - and the pointer works again. |

| D28 | **Counter movement is the only positive proof, and stillness is unknown.** Use the mouse (two-finger swipe) across two poll samples: `AclTranslateCount` (or `Rid12Count` when the first is absent) advances and the device row's scroll line reads as **working**. Not advancing must never be rendered or logged as a fault - an idle mouse and a broken one are the same read. |
| D29 | **Scroll help is user-initiated.** On a v3 `0323` whose bound filter is registered, RUNNING and **in** `DEVPKEY_Device_Stack`, the device row offers **Scroll problems? Get help**; the item is **absent** where that precondition does not hold (unbound, service stopped, filter not attached - those states are the automatic rules D2 / D12 / D18 instead). It is a question, not a verdict, so it is offered even while the scroll line above it reads **Scroll: working** - the user asserting the symptom is the point. Clicking it opens the guidance dialog: the numbered power-cycle (off, two seconds, on, then try the wheel) as the immediate step, install or restart the driver package's multitouch watcher as the permanent fix, **one** tri-state sentence about that watcher on this PC (running / not running / cannot tell), and - only when the file exists - a line naming `C:\ProgramData\MagicMouseDriver\auto-f1-watcher.log` as where the watcher records its own state. `debug.log` gets one `SCROLL_HELP_SHOWN pid=0323 watcher=` line reading `true`, `false` or `unknown`. OK opens the driver package page; Cancel or close touches nothing. |
| D30 | **Battery: one finding, and the deliberate silences.** A **connected Magic Keyboard** whose percent reads `-2` (SDP cache unpatched, or the patch erased by a re-pair; `KB_BATTERY_BLOCKED` / `KB_FEATURE_BLOCKED` in `debug.log`): exactly one row for that keyboard, routed to the existing **Fix battery reads** offer (`scripts/kbd-patch-cachedservices.ps1 -Mac <keyboard MAC>`, one elevated run, user-confirmed), and after it runs the percent appears. Then a **mouse** reading `-2`, `-3` or `-1` (leave `0323` idle until the tooltip says `Battery unavailable` / `No reading`): **no row, no toast, no repair** for any of the three. That silence is intentional - the percent is a pushed report, an idle mouse legitimately sends none, and the zeroed `0x90` pull is already rejected per D23 - so a finding there would nag every healthy PC daily. With that mouse row reading `Battery unavailable`, read the top row in the same menu open: it must say **No driver or connection problems found**, never an unqualified all-clear, so the header does not claim health for the one thing these checks never read. `debug.log` records both halves of that open - `REPAIR_FINDINGS raw=0 confirmed=0 pending=0` beside `REPAIR_SNAPSHOT pid=0323 ... batt=-2`. |

| D32 | **Guidance-only findings do not nag.** With a guidance-only state present (D7 zero instances, D8 phantoms only, or the D29 dialog left open/cancelled), leave the tray running across several poll ticks and open the menu repeatedly: the row stays, and the toast fires **once per problem per session** exactly as D10 requires - no repeat toast per tick, no repeated dialog, and no repair is ever attempted for a guidance-only finding. |
| D33 | **Transient install churn raises nothing.** While the driver package is being installed or the device restarted (`pnputil /restart-device`, or an install that briefly leaves the service Stopped, the filter out of `DEVPKEY_Device_Stack`, two rival filter names registered, or the COL01 pointer child absent), leave the tray running: `debug.log` shows `REPAIR_FINDINGS raw=N confirmed=0 pending=N held=<pid>:<Problem>` and **no toast, no dialog, no repair offer** appears while the state lasts under the hold window. | D34 | **Boot and resume re-check confirms a standing fault without a menu open.** Start the tray (or resume the PC from sleep) with a genuine fault present and then **do not touch the tray**: `debug.log` shows `HEALTH_SETTLE trigger=startup attempt=1/3`, `2/3`, `3/3` (resume logs `trigger=resume`), the finding goes `pending` then `confirmed`, and the toast fires on its own - measured on the reference PC 2026-09-15 18:43:12 / :29 / :46, confirmed at attempt 2. | D35 | **Driver advice in every state.** On a `0323` mouse, drive each driver state in turn - KMDF bound, patched Apple bound, stock Windows bound, nothing bound - and open the **Driver** submenu each time: it always shows exactly one advice line. | D36 | **Per-driver expectations are labelled as predictions.** The submenu lists one row per driver option beneath a header that states these are what each driver **would** give, not a reading of the live device. The patched Apple row reads as scroll **or** battery and never both at once. A Magic Keyboard and a Magic Trackpad show a single stock row on which scroll reads as not applicable and is **not** worded as broken, missing or failing. | D37 | **The battery flip, happy path.** On a `0323` bound to the patched Apple driver, open **Driver:** `Patched Apple` and click **Read battery now - stops the mouse for 10-20 seconds...**: exactly one confirmation dialog appears first, naming the 10-20 second pause in pointer and scrolling, the single administrator approval, and the guaranteed automatic restore with its check. Accept it: exactly **one** UAC prompt for the whole cycle, a battery percent is shown, and afterwards the scroll wheel scrolls again with the tray reporting the mouse verified back in scroll mode. `debug.log` shows the `MODE_FLIP` phases in order, records the verbatim previous `LowerFilters` value before it is changed, ends with `filters_match=true`, and clears the sentinel. Cancel at that dialog elevates nothing and writes nothing. |
| D38 | **The flip always restores.** Run the flip and kill the tray mid-cycle (Task Manager, during the pause), then separately run it again and let the reading fail (mouse switched off after the flip): in both cases the elevated script still writes back the **recorded previous** `LowerFilters` value, in its **recorded order**, and restarts the device, and the scroll wheel works afterwards. A failed reading is reported as a failed reading only - never as a failed or skipped restore, and never as a success. If the tray was killed before its own re-read confirmed that value, the sentinel survives (`sentinel=kept reason=restore-unverified`) and the next launch opens the startup restore offer: OK runs the one-click restore and the wheel comes back, Cancel leaves the offer for the next launch and touches nothing. The same recovery is reachable by hand at any time from **Driver -> Restore scroll mode**. |
| D39 | **The flip is refused where it does not apply.** On a KMDF-bound `0323`, on a v1 / v2 mouse (`030d` / `0269`), on a Magic Keyboard and on a Magic Trackpad, **Read battery now - stops the mouse for 10-20 seconds...** and **Restore scroll mode** are both **absent** from the menu - both are gated on the patched Apple driver. Invoke the underlying call directly anyway and it returns `NotPathA` without changing anything: no UAC prompt, no registry write, no `pnputil`, nothing restarted, and no `MODE_FLIP` phase beyond the refusal in `debug.log`. |
| D40 | **Configuration facts never nag a healthy PC.** With Test Mode on, Memory integrity off and the driver package present, the configuration section collapses to **System config: all checks passed** - nothing warning-shaped, no yellow or red wording, no offer to change anything - and each fact row under it reads `OK: <title>`. A device bound to stock Windows produces **no** configuration fact at all, and the section is hidden rather than claiming a check ran.
