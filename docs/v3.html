Why Magic Mouse v3 is not Magic Mouse v2

Magic Mouse 2024 (v3, USB-C, PID 0323) is a different Windows device from Magic Mouse v2 (Lightning, PID 0269). The v2 Boot Camp INF cannot name 0323. v3’s HID collections can also collapse after Bluetooth idle. “Install the Apple mouse driver” is the wrong instruction.

Primary sources

Kernel research lives in magic-mouse-v3-windows-fix (stripped from the public tray repo):

  • Bug analysis — DSM / BTHPORT cache
  • HID research — RID 0x90
  • Mode A/B diagram

Linux has in-tree hid-magicmouse (including USB-C v3). Windows does not. Apple’s redistributed Boot Camp mouse INF predates 0323.

v2: an INF that exists

v1 (030D) and v2 (0269) match AppleWirelessMouse.inf as shipped via tealtadpole. Catalog-signed. Test Mode not required. Magic Tray opens that INF; it does not invent a new v1/v2 kernel driver.

v3: no INF line, then the stack folds

0323 is missing, so Windows binds HidBth. Pointer often works. Wheel is missing or dies after idle.

Healthy v3 exposes two HID collections:

  • COL01 — cursor and scroll (Windows holds it; tray OPEN_FAILED err=5 is normal)
  • COL02 — battery. Tray reads Input 0x90 buf[2]. Not Feature 0x47. Not iPhone Hands-Free / WMI.

After idle, DeviceSetupManager can rewrite Bluetooth cached services so COL02 vanishes and COL01 collapses to one TLC. Scroll gone, cursor remains. Reboot does not restore Mode A. That is Mode B.

Patched Apple can pin scroll and drop battery. Stock can keep battery and drop scroll. KMDF is the path aimed at both. It is still self-signed — that is the funding goal.

Why a tray, not only a driver

A filter does not show 30% in the corner or refuse to patch the wrong keyboard MAC. v3 battery is userspace HID. Keyboard battery is an SDP registry patch. Trackpads are percent only. One .sys cannot cover that matrix — Devices.
