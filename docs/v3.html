Why Magic Mouse v3 is not Magic Mouse v2

Magic Mouse 2024 (v3, USB-C, PID 0323) is a different Windows device from Magic Mouse v2 (Lightning, PID 0269). The v2 Boot Camp INF cannot name 0323. v3’s HID collections can also collapse after Bluetooth idle. “Install the Apple mouse driver” is the wrong instruction.

Linux has in-tree hid-magicmouse (including USB-C v3). Windows does not. Apple’s redistributed Boot Camp mouse INF predates 0323.

v2: Apple already wrote a driver

v1 (030D) and v2 (0269) match AppleWirelessMouse.inf from tealtadpole. Catalog-signed. Test Mode not required. Magic Tray opens that INF; it does not invent a new v1/v2 kernel driver.

Magic Mouse v1 / v2

Lightning or AA. Apple listed these PIDs in Boot Camp.

Pair→Boot Camp INF→scroll works

Magic Mouse 2024 / v3

USB-C. PID 0323 is not in that INF. Windows uses generic Bluetooth HID.

Pair→no Apple driver→cursor yes, scroll dies

v3: two rooms, then Windows knocks the wall down

A healthy 2024 mouse talks to Windows as two rooms. After Bluetooth idle, Windows can merge them. Cursor stays. Scroll is gone. Reboot does not put the wall back. That is Mode B.

Their installer uses Apple’s signed applewirelessmouse.sys for v1/v2. Do not put that on Magic Mouse 2024 (0323). That PID still needs KMDF from magic-mouse-v3-windows-fix.

COL01

Cursor and scroll

Windows holds it; tray OPEN_FAILED err=5 is normal.

COL02 · Input 0x90

Battery

Tray reads buf[2]. Not Feature 0x47. Not iPhone Hands-Free / WMI.

Patched Apple can pin scroll and drop battery. Stock can keep battery and drop scroll. KMDF is the path aimed at both. It is still self-signed — that is the funding goal.

Why a tray, not only a driver

A filter does not show 30% in the corner or refuse to patch the wrong keyboard MAC. v3 battery is userspace HID. Keyboard battery is an SDP registry patch. Trackpads are percent only. One .sys cannot cover that matrix — Devices.
